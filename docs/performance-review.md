# 导入与缩放性能审查

当前实现已迁移至 Konva，新的验证结果见 [Konva 画布重构](konva-refactor.md)。下文保留此前 SVG 实现的诊断历史，旧回归脚本已由 Konva 套件替代。

日期：2026-09-21。范围：当前版本的照片导入、会话恢复、画布缩放。以下记录包含修复内容、验证结果与测量边界。

## 发现与修复

| 问题 | 原因与影响 | 修复 |
| --- | --- | --- |
| 开发构建导入单张照片约 10 秒 | 图像解码、缩略和编码依赖以未优化模式编译；真实 6000×4000 JPEG 的导入测试耗时 10.38 秒 | 仅对图像相关依赖开启开发构建优化，应用代码保留普通调试配置；同一测试降至 0.34 秒，约 30 倍提速 |
| Ctrl＋滚轮缩放漂移、默认行为冲突 | React 委托的被动监听无法取消默认行为；改变画布尺寸后没有同步补偿滚动位置，原复现累计漂移约 300 像素；deltaY=0 也会放大 | 原生非被动监听、按滚轮幅度累计并逐帧提交、绘制前补偿鼠标锚点、保留普通滚动；滑块和按钮使用视口中心锚点 |
| 批量导入和恢复长时间不显示画布 | 等待整批串行解码后才返回并显示；重复照片也先解码再去重；开发模式的 StrictMode 还可能启动两轮恢复 | 逐张接收和展示、显示进度、后续到达不改变当前照片、导入前去重；恢复优先处理活动照片，保留原顺序，抑制重复恢复任务和部分会话覆盖 |
| 浏览器预览占用原图资源 | Promise.all 同时解码整批，随后保留原图 Blob URL 用于列表及滤镜画布 | 串行解码，生成最长边不超过 720 像素的预览，及时关闭 ImageBitmap；保留原尺寸信息、PNG 透明度和坏文件隔离 |

## 验证

- `npm run build`、Rust 格式检查、Clippy `-D warnings`、`git diff --check` 通过。
- Rust 正常测试：6 项通过，显式运行的性能测试另行通过；覆盖真实 JPEG/EXIF 与带文字导出。
- Chromium 与 WebKitGTK 2.52 已运行画布与导入回归。补充复测中，WebKit 连续缩放两种照片比例的最大锚点漂移分别约 1.25 和 1.29 像素。滚动范围不足时画布仍按原规则居中，锚点测试根据窗口尺寸选择可滚动的起始倍率，另行检查进入滚动范围时不反向跳动。
- 原始画布测试保留，验证居中、裁切、逐帧合并滚轮事件及放大后的左边可达。
- Tauri 官方 IPC mock 驱动真实 App，验证首张不等待整批、坏文件隔离、重复导入跳过、后续到达不抢焦点，以及恢复时的顺序、选择、手动元数据和持久化保护。
- 浏览器导入回归使用自动生成的 4000×3000 PNG，确认预览为 720×540、原尺寸信息仍为 4000×3000。

## 测量边界

约 30 倍提速来自本机 **dev/test 构建**，不能外推为 release 提速；release 原本已启用优化。导入仍需完整解码单张原图，批量采用逐张处理以控制峰值，而非无限并发。200 张真实混合批次、9600 万像素原片峰值内存和实体触控板的交互验收仍未完成。

本次已验证 Rust 实际图片处理与两种引擎的前端交互；渐进导入与恢复的自动化交互使用 IPC mock。修改编译配置后需重新启动 `npm run tauri dev`；已有独立安装包需要重新构建才会包含修复。

## 后续复现：滚轮卡顿与点击跳位

用户反馈首轮修复后 Ctrl＋滚轮/触控板仍卡顿，点击元素后会突然移动。首轮的最终位置检查不足以覆盖绘制性能和指针交互，本轮补充如下修复。

- **WebKit 实时滤镜成本**：初始测量中，连续滚轮缩放单帧耗时中位数 82 ms、P95 140 ms；去掉实时滤镜后中位数/P95 均为 17 ms。现在将照片、模糊背景、圆角和阴影从同一份 SVG 栅格化为最长边不超过 1600 像素的缓存，水印和选框仍为可编辑矢量。缓存与缩放倍率、文字位置无关，照片或相框参数变化时失效，旧 Blob URL 会释放。WebKitGTK 不支持 Canvas2D.filter，因此不能直接照搬原型的 Canvas 滤镜实现。
- **缩放提交与输入**：缩放状态移至 EditorWorkspace，滚轮不再使照片列表与属性面板逐帧重渲染。沿用原型的指数缩放曲线，不再逐事件舍入小幅触控板输入；缩放与滚动补偿在同一个动画帧提交，避免下一帧的锚点被较晚的 React 提交消耗。画布贴边或尚无滚动空间时更新受限轴的锚点，避免跨越滚动边界后突然跳回。
- **滑块累计误差**：WebKit 往返滑块复现曾累计漂移 13.42 像素；现在保留精确中心锚点，区分用户滚动和程序补偿，补充回归中最大漂移约 1.12 像素。
- **点击被当成拖动**：文字边缘按下后仅移动 1 像素，原行为会让元素跳约 28 像素。现在移动达到 4 个屏幕像素才开始拖动，按下位置与元素中心的偏移始终保留；选择时聚焦不自动滚动画布。只接受当前主指针和主键拖动，正确处理捕获丢失。
- **快速松手的撤销**：指针移动后在下一次绘制前松手，原事务有时读取到旧文档。同步维护最新文档引用后，这类拖动同样可以一步撤销。

最终独立 WebKitGTK/Xvfb 性能复测：100% 起点的 48 帧往返滚轮序列，缓存就绪后首轮中位数 **23 ms**、P95 **46 ms**；相同缓存下重复序列中位数/P95 **17 ms**。这些是本机虚拟显示环境的测量，不能保证实体设备固定帧率；首轮缓存生成和首次绘制仍有成本。

WebKitGTK 的默认回归套件现覆盖 12 个检查步骤，包括缓存复用/失效/快速参数回退、滑块与滚轮边界、细小输入、点击/拖动/撤销及原有导入恢复。Chromium 另用真实鼠标验证：边缘按下并轻移的元素位移为 0；拖动 24×12 像素时实际位移约 24.000003×12.000015 像素，撤销可用。

性能诊断单独运行，不混入默认功能回归，以免其他测试抢占 CPU 影响测量：

```bash
xvfb-run -a python3 scripts/run-webkit-regressions.py http://127.0.0.1:1422 zoom-performance.js
```

## 高清编辑图补充（2026-09-21）

此前 720px 列表图参与照片主体绘制，且主体被合入 1600px 相框缓存，造成放大后细节丢失。现在主体按需读取最长边 4096px 的编辑图，背景缓存仍为 1600px；缩放复用纹理，水印拖拽不重绘照片。当前真实 6000×4000 JPEG 在 WebKitGTK 中首次/热缓存各 48 帧缩放采样 P95 均为 17ms，Chromium 分别约 16.8/16.7ms，均无超过 32ms 的帧。采样在高清图片就绪后开始，不包括首次解码。颜色空间与阴影一致性修复见 [渲染质量修复](render-quality.md)。

## 24MP 高清图加载（2026-09-24）

同一张 `PANA9432.JPG` 在本机 `tauri dev` 测试构建中，导入检查及高清编辑图生成合计 **2.8–3.0 秒**，其中再次解码约 0.22 秒、4096px 缩放约 0.8 秒、PNG 编码约 1.5 秒；传给 WebKit 的 data URL 约 **21 MB**。这解释了缩略图先出现、高清图几秒后才出现的现象。

JPEG 现在优先通过系统 `vips` 命令缩图并编码为质量 92 的 4096px JPEG。输出明确转换至 sRGB：默认缩图会保留像素数值却移除 ICC，带非 sRGB 配置的照片因此会偏色。临时文件放在自动清理的私有目录。若系统没有 `vips` 或处理失败，自动退回原有 Rust 解码、Lanczos 缩放与色彩管理路径；JPEG 回退也使用 JPEG 编码以减小传输量，PNG 仍保留无损和透明度。导出仍从原图独立渲染。

同一测试在加速路径下合计 **0.63–0.78 秒**，data URL 约 **2.62 MB**。测试覆盖 EXIF 旋转、嵌入 ICC 转换、PNG alpha 和编辑图尺寸。此测量只到 Tauri 返回 data URL，未计入 WebKit 最终解码和绘制；速度依赖本机可执行的 `vips`，无该工具的安装仍会使用较慢的回退路径。

```bash
vips --version
cargo test --manifest-path src-tauri/Cargo.toml --lib editor_photo_latency_budget -- --ignored --nocapture
```

# 0.1.2 导出可靠性验收

## 用户可见变化

- 同名文件在渲染期间出现时，保留该文件，按原设置重新编号或跳过。输出目录中的失效符号链接也视为已占用。
- 临时文件使用随机名称，失败、跳过和异常返回时自动清理。编码结束显式刷新缓冲区，写入失败不再报告成功。
- 清空元数据的显示值后，输出不再恢复原始 EXIF 文字。编辑器仍显示缺失字段提示，成品省略空文字。
- 失败重试使用上一次任务的照片、文档、文字覆盖和输出设置，不受后来切换照片或勾选范围影响。
- 批量任务中单张失败继续后续图片。取消完成当前图片再停止；最后一张已经完成时正常报告完成。
- PNG 使用标准 eXIf 块写入 EXIF，重新导入可读取相机参数；兼容 0.1.1 及以前导出的 PNG 文本块 EXIF。JPEG、PNG 均在编码时写入元数据，省去整张成品二次读写。
- 成品限制为单边 30000 px、总计 2.56 亿像素。预检和实际渲染同时校验；文字位图另有 6400 万像素限制。原先验证的 9600 万像素输入加边框仍在支持范围内。

## 已复现的失败与修复证据

| 场景 | 修复前结果 | 修复后验收 |
| --- | --- | --- |
| `finishing` 阶段创建同名文件 | `rename` 覆盖已有内容 | 原内容保留，编号/跳过两种策略均通过 |
| 向 `/dev/full` 编码小 PNG | 缓冲区尚未刷新，返回成功 | 返回写入错误 |
| 手动显示值为空或空白 | 回退原相机名称 | 返回空文本，预览缺失提示一致 |
| 超大边框、无限字号 | 请求校验放行 | 明确参数错误 |
| 30000px 近方形输出 | 预检放行，可能分配数 GB | 前后端均拒绝超预算画布 |
| 单张失败后重试，活动照片已变 | 从当前范围重新筛选，可能没有项目 | WebKit 界面测试重试原照片，完整请求保持一致 |
| JPEG→PNG 基础 EXIF→重新读取 | 写入器能读，应用读取器找不到 EXIF | 标准 PNG EXIF 可读，旧格式兼容测试通过 |

## 验证范围

- Rust 自动检查覆盖文件命名竞争、失效链接、缓冲写入错误、临时文件清理、队列错误隔离、取消边界、资源预算、超长文字、空覆盖值和元数据往返。
- 元数据矩阵：JPEG / PNG × 不保留 / 基础 / 支持的全部 EXIF × GPS 开 / 关；检查相机、作者策略、方向、输出尺寸及 sRGB ICC 保留。
- WebKit：导出参数校验、焦点进出、Escape、最新编辑内容、失败重试。
- 200 张连续导出使用两张本地 2400 万像素原片及一张由它们旋转生成的竖图，循环组成任务。JPEG、PNG 各 100 张，长边 1200px，默认宽留白模板，基础 EXIF。这验证持续处理与资源释放，不代表 200 张不同相机原片的兼容性覆盖。

最终 release 压力测试：200/200 成功，0 失败、0 跳过；导出 90.176s，含生成竖图替身的进程耗时 90.86s，峰值 RSS 288300 KiB（281.5 MiB）。每 25 张记录一次 RSS，JPEG 约 94–115 MiB，PNG 约 89–106 MiB，未观察到随张数增长的趋势。该数据对应本机一次持续处理测试，不能推断所有机器或原尺寸批量耗时。

最终自动测试：Rust 30 项通过、6 项显式性能/像素检查默认忽略；前端 17 项功能检查及入口体积检查通过；Clippy、TypeScript、格式检查通过。显式执行了上述 200 张压力测试和 WebKit 三项导出回归。

原尺寸性能复核（默认宽留白模板，真实 24MP 原片，每格式 3 次）：JPEG 中位数 2.377s，PNG 3.453s，峰值约 333 MiB；第一轮分别为 2.381s、3.650s。元数据修复未造成性能回退。
